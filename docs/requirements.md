## 1. 背景と目的

### 1.1 課題

紙の将棋書籍（棋書）には、内容の質とは別のところに構造的な不便さがある。

| # | 課題 | 具体的に何が起きるか |
| --- | --- | --- |
| C-1 | **盤面が動かない** | 読者が頭の中で駒を動かす必要があり、認知的な負荷が本題（戦法の理解）から逸れる。 |
| C-2 | **図と手順が追えなくなる** | 「第3図から▲7五歩△同歩▲同飛…」と続くうちに現在局面を見失う。「図◯に戻る」ためにページを行き来する。 |
| C-3 | **変化手順が線形に潰されている** | 本来は木構造である変化が、紙面では「（A）…（B）…」と直列に並ぶため、どの分岐にいるのか分からなくなる。 |
| C-4 | **検証できない** | 著者の推奨手が現代のAI基準でどう評価されるのか、その場で確かめられない。 |
| C-5 | **検索・再訪ができない** | 「あの形どの本に書いてあったか」を探せない。自分の気づきを書き込んでも後から引けない。 |

### 1.2 目的

**盤面が動く「読める・書ける・検証できる」将棋の本**を作るためのツールを提供する。具体的には、

1. 本文を読み進めると盤面が自動的に追従し、**現在局面を見失わない**（C-1, C-2 の解消）
2. 変化手順を**木構造のまま**表現・閲覧・編集できる（C-3 の解消）
3. 任意の局面から**将棋AIを呼び出して検証**できる（C-4 の解消）
4. 局面・戦法名・本文を**横断検索**でき、自分のメモを本と分離して残せる（C-5 の解消）
5. PCで本格的に執筆し、**スマホでも同等に読み書きできる**

### 1.3 非目的（このプロダクトがやらないこと）

- 対局プラットフォーム（オンライン対人戦）の提供
- 棋譜管理ソフト（ShogiHome / ShogiGUI）の完全な置き換え。棋譜ファイルの相互運用はするが、対局・大会運営機能は持たない
- 将棋AIそのものの開発。既存のUSIエンジンを利用する
- 商用の電子書籍ストア

## 2. ヒアリング結果（決定事項）

事前ヒアリングで確定した事項。本書の全設計はこれを前提とする。

| # | 論点 | 決定 |
| --- | --- | --- |
| D-1 | 提供形態 | **Webアプリ（PWA）を本体とし、本格的なAI連携はローカルの橋渡しプロセス経由**。PC・スマホ同一のアプリ。 |
| D-2 | コンテンツの用意方法 | ①自分で執筆・編集 ②既存の棋譜ファイル（KIF等）の取り込み ③既存の棋書を手入力で電子化 の3通り。**OCRは対象外**。 |
| D-3 | AI連携でやりたいこと | ①局面の解析・評価値表示 ②著者の手順とAI最善手の比較 ③AIと指して手順を確認。（LLMによる解説生成は今回スコープ外） |
| D-4 | 配布・運用 | **運用負荷ゼロが絶対条件**。GitHub Pages の静的サイトとして公開し、サーバ・DBは持たない。他人はURLを開けば使える。データは各自のブラウザ内に保存。 |
| D-5 | 必須機能 | 分岐ツリー管理 / 本文と盤面の連動 / 次の一手モード / 検索・しおり・メモ の**4つすべて**。 |
| D-6 | 技術スタック | TypeScript + React + Vite に一任。 |
| D-7 | コンテンツ共有 | **MVPでは共有・公開機能を作らない**（著作権上の整理を先送りするため）。アプリ自体は公開するが、本の配布機能は将来検討。 |
| D-8 | スマホでの編集 | **フル編集**。手順の入力・分岐の作成までスマホで行える必要がある。 |
| D-9 | 扱う内容 | 定跡書（序盤の戦法）/ 中終盤の手筋・寄せ / 詰将棋・必至問題 / 自分の対局の振り返り の**4種すべて**。 |
| D-10 | AI導入の手間 | 「ShogiGUIでエンジンを登録するのと同程度」を許容。ブラウザ内WASMエンジンの強さは未知数のため、**両方使える構成**とする。 |
| D-11 | ホスティング | **GitHub Pages のみ。他のサービスは使わない**（Q-1 の決定）。 |
| D-12 | 盤面 | **shogi-player（akicho8 氏）を採用**。自作盤は廃止。これに伴い本プロダクトのライセンスは **AGPL-3.0** となる。 |
| D-13 | 紙面の構造 | **ページめくり型に確定**（見比べた結果）。スクロールと連動は代替として残すが既定ではない。「章＝ページ」は役目を終えたため削除。 |
| D-14 | 図面の振る舞い | **「図ごとに手順を持ち、その場で進める」に確定**。静止図・主図ひとつは採らない。 |
| D-15 | 組方向 | 既定は横書き。**縦書きに切り替えられる**こと。 |
| D-16 | 分岐ツリーの向き | 縦・横を切り替えられること。既定は縦。 |

### 2.1 D-4 と D-3 の緊張関係について（重要）

「サーバを持たない」と「本格的な将棋AIを使う」は、そのままでは両立しない。ブラウザのセキュリティモデル上、**Webページから利用者のPC上の `.exe`（USIエンジン）を直接起動することはできない**ためである。

本書ではこれを **2つの動作モード**を用意することで解決する（第9章）。要旨は以下の通り。

- **通常モード**：GitHub Pages 上のアプリ。AIはブラウザ内で動くWASM版エンジンを使う。インストール不要で誰でも使える。
- **ローカルモード**：利用者のPCで小さなブリッジプログラムを起動する。ブリッジが**アプリ自身を配信し、かつ USIエンジンを橋渡しする**。ShogiGUI相当のエンジン登録ができ、水匠などのネイティブエンジンをフル性能で使える。

この「ブリッジがアプリも配信する」という設計は、単なる思いつきではなく、第10章で述べる**2つのブラウザ制約を同時に回避する**ための選択である。

## 5. 機能要件

優先度は **MUST**（MVP必須） / **SHOULD**（MVPに入れたい） / **COULD**（第二版以降）で示す。

### F-1. 本棚・本の管理

| ID | 要件 | 優先度 |
| --- | --- | --- |
| F-1-1 | 本の一覧を表示する（タイトル、更新日時、章数、進捗）。 | MUST |
| F-1-2 | 本を新規作成・複製・削除・リネームできる。削除は確認を挟み、一定期間の復元手段を持つ。 | MUST |
| F-1-3 | 本にタグ（戦法名、著者、分類）を付与し、タグで絞り込める。 | SHOULD |
| F-1-4 | 本の種別（定跡書 / 手筋集 / 問題集 / 対局ノート）を設定でき、種別に応じて既定の編集UIが変わる。 | SHOULD |
| F-1-5 | 本のメタデータとして「出典」「私的利用フラグ」を保持する（D-7 に関連。将来の共有機能の前提となる）。 | SHOULD |

### F-2. 閲覧（本文と盤面の連動）— 本プロダクトの中核

| ID | 要件 | 優先度 |
| --- | --- | --- |
| F-2-1 | 画面を「本文ペイン」と「盤面ペイン」に分割して表示する。 | MUST |
| F-2-2 | **本文をスクロールすると、表示中の段落に紐づく局面へ盤面が自動追従する**（C-2 の直接的な解決）。 | MUST |
| F-2-3 | 逆に、盤面側で手を進めると、対応する本文へ自動スクロールする（双方向連動）。 | MUST |
| F-2-4 | 自動追従はON/OFFを切り替えられる。OFFのとき、本文と盤面は独立に動く。 | MUST |
| F-2-5 | 本文中の指し手表記（▲7六歩 等）はクリック可能で、押すとその局面まで一気に進む。 | MUST |
| F-2-6 | 盤面に「1手戻る／1手進む／分岐の初手へ／最終手へ」の操作を提供する。キーボード（←→）でも操作できる。 | MUST |
| F-2-7 | 直前の一手を盤上でハイライトする。 | MUST |
| F-2-8 | 持ち駒を盤の上下に表示する。駒台の駒数を明示する。 | MUST |
| F-2-9 | 盤面反転（先手視点／後手視点）を切り替えられる。 | MUST |
| F-2-10 | 手順を自動再生（1手/秒など、速度可変）できる。 | COULD |
| F-2-11 | 駒の移動をアニメーションで表示する（OFF可）。 | COULD |
| F-2-12 | 本文中に静止図を明示的に置ける（「第3図」相当）。紙の本の再現性のため。 | SHOULD |

**F-2-2 の設計上の注意**：スクロール連動は「気持ちよさ」が価値の大半を占める機能であり、実装の粗さが致命的な体験劣化に直結する。具体的なリスクは、(a) 追従が過敏でスクロール中に盤面がちらつく、(b) 追従アニメーション中のユーザー操作を奪ってしまう、(c) 双方向連動が無限ループする。**MVPのプロトタイプでは、まずこの1機能だけを作って手触りを確認すること**を強く推奨する。

### F-3. 分岐（変化手順）ツリー

| ID | 要件 | 優先度 |
| --- | --- | --- |
| F-3-1 | 1つの手順を木構造として保持する。任意のノードから複数の子（変化）を持てる。 | MUST |
| F-3-2 | 分岐ツリーを可視化する。現在位置、本筋、変化を視覚的に区別する。 | MUST |
| F-3-3 | ツリー上のノードをクリックすると、その局面へジャンプする。 | MUST |
| F-3-4 | 現在局面から分岐が存在する場合、盤面上またはツリー上でそれを示唆する（読者が変化の存在に気づける）。 | MUST |
| F-3-5 | 分岐に名前を付けられる（例：「△4二銀型」）。 | SHOULD |
| F-3-6 | 分岐の並べ替え（どれを本筋にするか）ができる。 | SHOULD |
| F-3-7 | 同一局面に異なる手順で到達した場合の合流（トランスポジション）を検出し、通知する。 | COULD |
| F-3-8 | スマホでは、ツリーを常時表示せず、必要時に引き出す（ボトムシート等）。 | MUST |

**F-3-2 の設計上の注意**：定跡書は分岐が深く多いため、ツリー表示は容易に画面を溢れさせる。「全体を俯瞰する図」と「現在地周辺だけを示す簡易表示」の2段構えが必要になる見込み。詳細はUI設計フェーズで詰める。

### F-4. 編集

| ID | 要件 | 優先度 |
| --- | --- | --- |
| F-4-1 | 盤面上で駒を動かすと、現在ノードの子として手が追加される。既存の手と同じなら既存ノードへ進む。 | MUST |
| F-4-2 | 既存の手と異なる手を指した場合、新しい分岐として追加するか確認する（あるいは既定で分岐追加）。 | MUST |
| F-4-3 | 合法手のみを受け付ける。非合法手は理由とともに拒否する。 | MUST |
| F-4-4 | 成／不成の選択、駒打ちに対応する。 | MUST |
| F-4-5 | 手を削除できる（以降の手順も含めて削除する旨を明示）。 | MUST |
| F-4-6 | 任意のノードに解説文（本文ブロック）を紐づけられる。 | MUST |
| F-4-7 | 本文はリッチテキストではなく **Markdown ベース**とする（可搬性・将来のエクスポート容易性のため）。 | MUST |
| F-4-8 | 本文中に指し手参照を挿入できる（F-2-5 のリンクになる）。 | MUST |
| F-4-9 | 章・節の追加、並べ替え、削除ができる。 | MUST |
| F-4-10 | **任意局面エディタ**：初期局面を平手以外（中終盤の局面、駒落ち、詰将棋の図）に設定できる。駒箱から盤・駒台へ配置し、手番を指定する。 | MUST（D-9 により必須） |
| F-4-11 | 任意局面の正当性を検証する（二歩、行き所のない駒、王手放置、玉の数など）。不正な場合は保存前に警告する。 | MUST |
| F-4-12 | 編集内容は自動保存される。保存中／保存済みの状態が分かる。 | MUST |
| F-4-13 | Undo / Redo（最低20段階）。 | SHOULD |
| F-4-14 | **スマホでの編集**：タッチでの駒移動、分岐追加、本文編集がすべて可能であること。片手操作を想定し、主要操作は画面下部に配置する。 | MUST（D-8） |

**F-4-10 について**：D-9 で「中終盤の手筋」「詰将棋」を扱うと決まったため、任意局面エディタは MVP 必須である。当初「定跡書だけなら平手初期局面で足りる」と考えていたが、この決定により前提が変わった。実装コストは小さくない（駒箱UI、持ち駒の増減、局面検証）ので、見積りに含めること。

### F-5. 次の一手（問題）モード

| ID | 要件 | 優先度 |
| --- | --- | --- |
| F-5-1 | 本の任意の箇所を「問題」として指定できる。問題は「局面 + 正解手（複数可） + 解説」で構成する。 | MUST |
| F-5-2 | 問題モードでは、正解手・以降の手順・解説を伏せて出題する。 | MUST |
| F-5-3 | 読者が盤面で手を指すと、正誤を判定して結果を表示する。 | MUST |
| F-5-4 | 不正解時に、解説（なぜその手が悪いか）を表示できる。著者が「よくある間違い」ごとに個別の解説を書ける。 | SHOULD |
| F-5-5 | 正解が複数手順（詰将棋の5手詰など）の場合、手順全体を入力させる。途中で誤ればその時点で不正解とする。 | MUST（D-9 で詰将棋を扱うため） |
| F-5-6 | 詰将棋については、エンジンによる詰み判定・余詰めチェックを行える。 | COULD（L-6 と併せて第二版） |
| F-5-7 | 問題の成績（正答率、最終挑戦日）を記録する。 | SHOULD |
| F-5-8 | 間隔反復による復習キューを提供する（誤った問題を後日再出題）。 | COULD |
| F-5-9 | 1冊の本から問題だけを抽出して連続出題できる。 | SHOULD |

### F-6. 検索・しおり・メモ

| ID | 要件 | 優先度 |

**WASMエンジンの強さについて（D-10 のご質問への回答）**：
オンライン将棋サイト **lishogi.org は、局面解析とAI対局に、やねうら王のWebAssembly版（NNUE評価関数つき）を採用している**。実運用に耐える強さであることは、この採用実績が示している。
ただしネイティブ版（水匠等）と比べると、**同じ思考時間あたりの探索量では劣る**。理由は、(a) WebAssembly自体のオーバーヘッド、(b) 利用できるスレッド数の制約、(c) ブラウザに載せられる評価関数ファイルのサイズ上限。したがって「アマチュアの検討には十分すぎる強さだが、ネイティブ最強構成には及ばない」という位置づけになる。
本書が **F-8-9（WASM）を MUST、F-8-10（ネイティブ）を第二版**としているのはこの理解に基づく。まずWASMで動くものを作り、実際に使ってみて物足りなければローカルエンジン連携を入れる、という順序であれば、判断材料を持った状態で決められる。

## 7. データモデル

### 7.1 設計方針

**「文章の列」と「手順の木」を別の構造として持ち、文章側から手順側のノードを参照する**という構成を採る。

この選択には理由がある。素朴な設計は「手順の各ノードにコメントを付ける」（KIF等の棋譜フォーマットと同じ構造）だが、これでは棋書を表現できない。棋書の本文は、
- 手順の前に置かれる導入文（まだどの局面でもない）
- 1つの局面について数段落にわたる長い解説
- 複数の変化をまたいでの総括

を含み、「1ノード=1コメント」に収まらないためである。逆に「本文だけ」の構造にすると分岐ツリーが表現できない。両者を分離し、参照で結ぶのが素直である。

### 7.2 構造の概要

```
Book（本）
├── meta: タイトル、著者、種別、タグ、出典、私的利用フラグ、スキーマ版
├── chapters: Chapter[]
│   └── Chapter（章）
│       ├── title
│       ├── rootPosition: SFEN          … 章の初期局面（平手 or 任意局面）
│       ├── moveTree: MoveNode           … 手順の木（1章に1本）
│       └── blocks: ContentBlock[]       … 本文ブロックの列
└── (別レイヤー) annotations: Annotation[]  … 読者メモ。本文を汚さない
```

#### MoveNode（手順ノード）

| フィールド | 型 | 説明 |
| --- | --- | --- |
| id | string | ノードID |
| move | Move \| null | 直前の指し手（ルートはnull） |
| sfen | string | この局面のSFEN。検索・キャッシュのため保持 |
| children | MoveNode[] | 子ノード。先頭を本筋とする |
| label | string? | 分岐名（F-3-5） |
| evaluation | Eval? | エンジン解析結果のキャッシュ（F-8-12） |

#### ContentBlock（本文ブロック）

| フィールド | 型 | 説明 |
| --- | --- | --- |
| id | string | ブロックID |
| type | 'text' \| 'diagram' \| 'quiz' | 種別 |
| nodeId | string? | 紐づく手順ノード。**これが本文↔盤面連動の実体**（F-2-2） |
| markdown | string | 本文（type='text'） |
| quiz | Quiz? | 出題定義（type='quiz'、F-5） |

#### Quiz（問題）

| フィールド | 型 | 説明 |
| --- | --- | --- |
| answerNodeIds | string[] | 正解手順のノード列（複数手順に対応、F-5-5） |
| acceptableFirstMoves | Move[] | 正解として認める初手（複数正解、F-5-1） |
| wrongMoveComments | Map<Move, string> | よくある間違いへの個別解説（F-5-4） |
| explanation | string | 解説 |

#### Annotation（読者メモ）

| フィールド | 型 | 説明 |
| --- | --- | --- |
| bookId / chapterId / nodeId | string | 紐づけ先 |
| markdown | string | メモ本文 |
| createdAt / updatedAt | number | 日時 |

### 7.3 補足

- **SFENをノードに持つ理由**：局面検索（F-6-2）と解析キャッシュ（F-8-12）を、木を辿り直さずに実現するため。冗長だが、容量よりも検索速度と実装単純性を優先する。
- **スキーマバージョン**：F-7-8 の通り、Book.meta にスキーマ版を持たせ、読み込み時にマイグレーションを噛ませる。長く使うツールなので初版から必須とする。
- **正規化**：局面検索の一致判定には、持ち駒の順序や手数を除いた正規化SFENを用いる。

## 9. アーキテクチャ

### 9.1 2つの動作モード

```
【通常モード】— 誰でも使える。インストール不要。
  ブラウザ
   ├── shogiXbook（GitHub Pages から配信）
   ├── IndexedDB（本・メモ・設定）
   └── YaneuraOu.wasm（Web Worker 内で動作）
  ※ サーバ・DB・アカウント一切なし → 運用負荷ゼロ（D-4 を満たす）

【ローカルモード】— 本格的にAIを使う人向け。第二版。
  PC
   ├── shogiXbook-bridge（単一実行ファイル）
   │    ├── http://localhost:8765 で shogiXbook 本体を配信  ★1
   │    ├── COOP/COEP ヘッダを付与                          ★2
   │    └── WebSocket で USIエンジンを橋渡し
   │         └── 子プロセス: YaneuraOu.exe / suisho.exe ...
   └── ブラウザ → http://localhost:8765 を開く
```

### 9.2 ★1「ブリッジがアプリ自身を配信する」理由

一見すると回りくどい。「GitHub Pages のアプリから `ws://localhost` でブリッジに繋げばよいのでは」と考えるのが自然である。しかしこれは**Safari で動作しない**。HTTPSページから `ws://` への接続は混在コンテンツ（mixed content）としてブロックされ、Chrome は localhost を例外扱いするが、**Safari は localhost であってもブロックする**。iPad や Mac の Safari で使えないのは受け入れがたい。

ブリッジ自身が `http://localhost:8765` でアプリを配信すれば、アプリとブリッジが同一オリジンになり、混在コンテンツの問題そのものが消滅する。

### 9.3 ★2「COOP/COEP ヘッダ」— GitHub Pages の制約（重要）

YaneuraOu.wasm のマルチスレッド版は `SharedArrayBuffer` を必要とし、これを使うには HTTP レスポンスヘッダに

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

が必要である。ところが **GitHub Pages は独自のレスポンスヘッダを設定できない**。つまり通常モードでは、素直に作るとマルチスレッド版WASMエンジンが動かない。

対処は3案ある。

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | Service Worker で COOP/COEP を注入する（`coi-serviceworker` として知られる手法） | GitHub Pages のまま解決できる。初回アクセス時にリロードが1回挟まる、他オリジンのリソース読み込みに制約が出る等の副作用あり。**第一候補** |
| B | シングルスレッド版WASMを使う | 確実に動くが探索性能が落ちる。**フォールバックとして必ず用意する** |
| C | ヘッダを設定できるホスティング（Cloudflare Pages 等）に変える | 解決するが、D-4「GitHub Pages」の決定を覆すことになる |

**方針（確定）**：**C 案は採らない。GitHub Pages で通す**（Q-1 の決定。他サービスを増やさない方針による）。Bを既定の動作保証ラインとし、Aを上乗せする。Aが環境によって効かない場合もBで動き続ける設計にする。

なお開発サーバ（Vite）では COOP/COEP を直接設定できるため、エンジン組み込みの検証自体はローカルで問題なく行える。GitHub Pages 固有の制約が顕在化するのは P3（AI連携）以降であり、それまでは A/B の実装を先送りしてよい。

### 9.4 データフロー

- 本の保存・読み込みはすべてローカル（IndexedDB）。ネットワーク越しの永続化は行わない。
- エンジンとの通信は USI プロトコル。通常モードは Worker 経由のメッセージング、ローカルモードは WebSocket。**アプリ側から見たインターフェースは同一に抽象化する**（`EngineAdapter`）ことで、F-8-9 と F-8-10 を同じ上位コードから使えるようにする。

## 10. 技術的制約とリスク

| ID | リスク | 影響 | 対策 |
| --- | --- | --- | --- |
| R-1 | **GitHub Pages で COOP/COEP を設定できず、マルチスレッドWASMが動かない** | AI解析の性能低下 | 9.3 の通り。シングルスレッド版をフォールバックに、Service Worker 方式を上乗せ。またはホスティング変更（🔴要判断） |
| R-2 | **HTTPS ページから `ws://localhost` が Safari でブロックされる** | ローカルモードが Safari で使えない | 9.2 の通り、ブリッジ自身がアプリを配信する構成で回避 |
| R-3 | **IndexedDB のデータがブラウザに削除されうる**（ストレージ逼迫時の自動退避、履歴削除操作） | **本の消失＝致命的** | ①`navigator.storage.persist()` で永続化を要求 ②初回起動時に「データはこの端末内にのみ保存される」と明示 ③定期的なエクスポートを促す ④F-7-6 のエクスポートを常に1クリックで実行可能にする |
| R-4 | iOS Safari の PWA はストレージ容量・寿命の制約が相対的に厳しい | スマホでの本の消失 | R-3 と同じ。加えてスマホでは「編集したらエクスポート」を促す導線を強めに置く |
| R-5 | 端末間で自動同期しないため、PCとスマホで別々に編集すると内容が分岐する | 編集の衝突・喪失 | MVPでは「同時編集しない」ことを前提とし、UIで最終更新端末・日時を明示する。将来 L-5 で解決 |
| R-6 | WASMエンジンのファイルサイズ（評価関数含む）が大きく、初回読み込みが重い | モバイル回線での体験劣化 | エンジンは遅延読み込みとし、解析を使うまでダウンロードしない。キャッシュ後は再ダウンロード不要 |
| R-7 | スマホでの盤面タッチ編集の操作性が想定より悪い | D-8 の要求を満たせない | プロトタイプ段階で実機検証を行う。MVPの中で最優先の検証項目とする |
| R-8 | 本文↔盤面のスクロール連動が不自然になる | 中核価値の毀損 | F-2-2 の注記の通り、単独プロトタイプで手触りを先に確認する |
| R-9 | 分岐ツリーが巨大化した際の描画性能 | 定跡書で実用に耐えない | 仮想化・部分描画。ツリー表示は「俯瞰」と「近傍」の2モード |
| R-10 | KIF の文字コード（Shift_JIS）誤判定 | インポート失敗・文字化け | F-7-7。判定失敗時に手動で文字コードを指定できる導線を用意 |
| R-11 | **shogi-player が AGPL-3.0** | 本プロダクトも AGPL-3.0 になる | 公開して誰でも使えるようにする方針と矛盾しないため受け入れる（D-12）。LICENSE を同梱済み |
| R-12 | **shogi-player が gzip 約 1.8MB** | 初回読み込みが重い（本体の約 20 倍） | 盤を表示する段になってから遅延読み込みする。別チャンクに分離済みで、キャッシュ後は再取得しない |
| R-13 | **shogi-player が Vue 2 ベース**（2023年末に EOL） | 将来の保守リスク | 依存を `src/board/` の 2 ファイルに閉じ込め、差し替え可能にしてある |
| R-15 | 図面が棋書の見た目にならない | 「本らしくない」という体験上の問題に直結する | 盤は shogi-player の紙面風の駒（`paper`）と地模様なしの盤を使い、罫線・座標・駒の大きさを `sp_pass_css` で棋書寄りに上書きする（`src/board/kishoStyle.ts`）。**持ち駒がないときの手番マークは棋書の「持駒 なし」表記と異なる**ままで、ここは未解決 |
| R-16 | view モードでも盤上の駒を自由に動かせてしまう | 読み物の図が編集画面に見える | shogi-player は `sp_overlay_nav` が false のとき view でも駒を動かせる仕様。view では既定で true にして塞いだ |
| R-14 | **shogi-player が実行時に外部 CDN からアイコンを取得する** | オフラインで表示が崩れ（NF-6）、外部へ通信が飛ぶ（NF-8） | URL がバンドルに直書きされているため、ビルド時に自前配信へ差し替える（`vite.config.ts` の selfHostMdi と `scripts/vendor-mdi.mjs`）。差し替え漏れはビルド時に警告する |

### 10.1 著作権に関する整理（D-7 関連）

D-2③（既存の棋書を手入力で電子化）と、他人への提供は、法的な性質が異なる。

- **自分が購入した棋書の内容を、自分だけが使う目的で入力する行為**は、私的使用のための複製の範囲として一般に理解されている。
- 一方、**それを第三者に配布・公開する行為**は権利者の許諾なしには行えない。

D-7 のご判断（MVPでは共有機能を作らない）は、この論点を実装前に確定させずに済むという意味で妥当である。本書では以下の方針を採る。

1. MVPでは本を他人に渡す機能を実装しない（L-4）。
2. ただし **F-1-5 で「出典」「私的利用フラグ」をデータモデルに含めておく**。将来 L-4 を実装する際、既存棋書由来の本を機械的に共有対象から除外できるようにするための布石である。後から足すとデータ移行が必要になるため、初版から入れておく価値がある。

⚠️ 上記は法的助言ではない。実際に共有機能を実装する段階では、必要に応じて専門家の確認を得ることを推奨する。

## 14. 用語

| 用語 | 説明 |
| --- | --- |
| SFEN | 将棋の局面を1行の文字列で表す記法。局面の一意な識別に用いる |
| USI | Universal Shogi Interface。将棋GUIとエンジンの通信プロトコル |
| KIF / KI2 / CSA / JKF | 棋譜ファイル形式。KIF・KI2 は日本語表記、CSA は英数字、JKF は JSON ベース |
| NNUE | ニューラルネットワークを用いた将棋の評価関数方式 |
| PV | Principal Variation。エンジンが最善と考える読み筋 |
| MultiPV | 複数の候補手とその読み筋を同時に出力する機能 |
| PWA | Progressive Web App。Webアプリをネイティブアプリのようにインストール・オフライン利用できる仕組み |
| COOP / COEP | ブラウザのセキュリティ関連レスポンスヘッダ。`SharedArrayBuffer` の利用に必要 |
| トランスポジション | 異なる手順で同一局面に到達すること |
