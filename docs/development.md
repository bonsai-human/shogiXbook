## 現況

**紙面の構造を決めるための「見比べ用プロトタイプ」。**

画面右上の「見比べ」を押すと、紙面の構造・図面の振る舞い・組方向・分岐ツリーの向きを
その場で切り替えられる。決まったら切り替え UI は畳んで既定を固定する。

| 切り替え | 選択肢 |
| --- | --- |
| 紙面の構造 | ページめくり（リフロー） / 章＝ページ / スクロール（図は本文埋め込み） / 連動（初版） |
| 図面の振る舞い | ①その場で進む ②静止図＋タップで拡大 ③主図ひとつ |
| 組方向 | 横書き / 縦書き |
| 分岐ツリー | 縦に伸ばす / 横に伸ばす |

**フェーズ P0 相当（検証プロトタイプ）まで。**

ロードマップ（要件定義書 12 章）の P0 は「①本文↔盤面のスクロール連動 ②スマホでの盤面タッチ編集 の 2 点だけを作り、手触りを確かめる」ことを目的としている。これは、この 2 点が要件の中で最も「作ってみないと分からない」部分であり、うまくいかなければ設計全体を見直す必要があるため。

そのため現時点では、**保存機能がない**。リロードすると編集内容は消える。これは未実装ではなく、P0 の目的に対して不要だから入れていない。

### 設計上の要点

**本文と手順を別構造にしている。** 素朴には「棋譜の各手にコメントを付ける」（KIF 等と同じ構造）となるが、それでは棋書を表現できない。導入文・1 局面に数段落の解説・複数の変化をまたぐ総括が「1 ノード = 1 コメント」に収まらないため。詳細は `src/types/book.ts` の冒頭コメント。

**各ノードに SFEN を持たせている。** 冗長だが、局面検索（F-6-2）と解析キャッシュ（F-8-12）を木の辿り直しなしで実現するための意図的な選択。

**スクロール連動は IntersectionObserver で「読んでいる帯」を判定している。** スクロール量に逐一反応させると盤面がちらつくため。双方向連動の無限ループは、盤面側の操作で本文をスクロールしている間だけ本文→盤面の追従を止めることで防いでいる（`Reader.tsx` の `SUPPRESS_MS`）。

**`.reader` が PC・スマホのいずれでも唯一のスクロール領域。** IntersectionObserver の root として使い、帯の位置を割合で指定しているため。ページ全体がスクロールする構成に変えると連動が壊れる。これは連動レイアウトにのみ関係する。

**ページめくりのリフローは CSS の段組みに任せている。** 自前で高さを測って詰めるのではなく、1 段の幅を紙面の幅に合わせ、高さを固定して `column-fill: auto` にすると、ブラウザが内容を上から順に段へ流し込む。これがそのままページ分割になる。段落の途中で切れる自然な分割まで含めてブラウザ任せにできる。なお `column-width` はパーセント指定を受け付けないので、幅は実測値（px）で渡す必要がある。

**縦書きではページ送りの実装が変わる。** 縦組みでは内容が右方向へ伸び、章の先頭が最大スクロール位置にくる。平行移動だと座標の向きの解釈が環境依存になるため、縦書きのときだけ `scrollBy` で送っている。

**shogi-player は分岐を扱えない。** `sp_body`（KIF か SFEN）＋ `sp_turn`（手数）という直線的なモデルで、KIF パーサに変化の処理がない。そのため木構造は shogiXbook 側が持ち、現在たどっている経路を `position sfen ... moves ...` に平坦化して渡している（`src/shogi/usi.ts`）。指し手は局面全体の文字列で返ってくるので、送った内容との差分から新しい手を取り出す。

## 調整したい値

P0 の目的は数値の作り込みではなく手触りの確認なので、以下は暫定値のまま。実機で触って決める。

| 場所 | 値 | 内容 |
| --- | --- | --- |
| `Reader.tsx` `READING_BAND` | `-12% 0px -76% 0px` | 「読んでいる行」とみなす帯の位置 |
| `Reader.tsx` `SUPPRESS_MS` | `700` | 盤面操作後、本文→盤面の追従を止める時間 |
| `PagedLayout.tsx` `PAGE_GAP` | `48` | ページどうしの間隔（px） |
| `styles.css` `.paged-viewport` | `max-width: 46rem` | ページめくり時の紙面の幅 |

## デプロイ

`main` への push で GitHub Actions が GitHub Pages へ公開する（`.github/workflows/deploy.yml`）。

初回だけリポジトリ設定が必要:
**Settings → Pages → Build and deployment → Source** を **GitHub Actions** にする。

公開先は `https://bonsai-human.github.io/shogiXbook/`。base パスはワークフローがリポジトリ名から自動で与えるので、リポジトリ名を変えても追随する。

## shogi-player について

盤面の描画・操作・局面編集は [shogi-player](https://github.com/akicho8/shogi-player)（akicho8 氏、AGPL-3.0）に任せている。これに伴い本プロダクトも **AGPL-3.0** となる（LICENSE 同梱）。

採用にあたって手当てした点:

- **外部 CDN への通信を止めた。** shogi-player は Shadow DOM 内のスタイルシートから jsDelivr の Material Design Icons を `@import` する。URL がビルド済みバンドルに直書きされており props では変えられないため、ビルド時に自前配信の URL へ差し替えている（`vite.config.ts` の `selfHostMdi`）。フォントの配置は `node scripts/vendor-mdi.mjs` で行い、`public/vendor/mdi/` に置く。**shogi-player を更新したらこの差し替えが効いているか確認すること**（効かなくなるとビルド時に警告が出る）。
- **遅延読み込みにした。** gzip で約 1.8MB あり、アプリ本体（約 80KB）の 20 倍以上ある。盤を表示する段になってから読み込み、別チャンクに分離してある。
- **依存を閉じ込めた。** `src/board/` の 2 ファイル以外は shogi-player を知らない。Vue 2 ベース（2023年末に EOL）なので、将来差し替える可能性を考えてこの形にしている。

## 既知の制約

- **GitHub Pages は COOP/COEP ヘッダを設定できない。** 将来 WASM エンジンのマルチスレッド版を使う際に効いてくる（要件定義書 9.3 / R-1）。開発サーバ側には `vite.config.ts` で設定済みなので、ローカルでの検証は問題なく行える。
- **保存機能がないため、リロードで編集内容が消える。** P1 で IndexedDB に載せる。
- **縦書きは横書きより作り込みが浅い。** 段落の組みや図の回り込みは詰めていない。切り替えて確認できる段階まで。
